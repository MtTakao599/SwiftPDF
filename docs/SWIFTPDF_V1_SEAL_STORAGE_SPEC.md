## 1. 対象ソースと現行仕様（SWSEAL1）

根拠は `crates/ui-egui/src/seal_store.rs`、`stamps_ui.rs`、`editing.rs`、`crates/platform/src/{dpapi,staging}.rs`（`c740330`）である。

### ファイルの構造

- `seals.bin` は、`MAGIC = b"SWSEAL1\n"`（8 バイト、平文）と、その直後の DPAPI 暗号文だけでできている。
  - `write` が `MAGIC` と `protect_user(plain)` を連結する。
  - `decode_file` は `strip_prefix(MAGIC)` で境界を取る。
- DPAPI で保護するのは、平文 JSON の全体である。ヘッダーは保護されない。
- 平文は `FileBody { seals: Vec<StoredSeal>, history: Vec<StoredEvent> }`（`serde_json`）。
  - `StoredSeal`: `name, file, width, height, data（PNG の base64）, scale, effects`
  - `StoredEvent`: `at, file, page, seal, event, processed, angle_deg, fade, seed, image_sha256, rotation_mode`

### 識別子

- 印影は `name` で区別する（`add_seal` が重複を拒否する）。UI は添字 `QuickTool::ChairmanSeal(index)` で扱う。ID は無い。
- 履歴の行に ID は無い。`event` は `confirmed | undone | redone | removed | removal-undone` の 5 種類（`append_event` と `decode_file` が検査する）。
- 承認と使用は、同じ `history` に 1 行の `confirmed` として入る。

### 書き込み

- `persist` → `write` → `staging::write_atomically(path, bytes, TagThenSuffix)` の順に進む。
  - 書き込みは、新しい一時ファイルの作成（`create_new`）、`write_all`、`sync_all`、`rename` の順である。
  - 失敗すると、一時ファイルを消し、メモリを `previous` に戻す。
- 400 行上限: `append_event` が `drain(0..extra)` で古い行を消す。`decode_file` は 400 行を超えるファイルを拒否する。

### 呼び出しの順序

- **押印**（`stamps_ui.rs` 2723〜2793）:
  1. 承認スナップショットを照合する（`approval_matches` と、押す PNG の SHA-256）。
  2. `append_event(confirmed)` で記録する。失敗したら押さない。
  3. `apply_edit(AddCustomStamp)` で文書に入れる。
  4. 適用に失敗したら `pop_event`（最後の行を物理的に削除）。
  5. 成功したら `seal_uses` に積む。
- **注釈削除**（`editing.rs` 58〜70、203〜208）: `append_event(removed)`、続いて適用する。失敗したら `pop_event`。
- **Undo / Redo**（`note_seal_history_step`）: 文書の変更の後に記録する。記録に失敗したら、文書を戻す。

### 権限の確認

- 印影の登録・更新・削除には、ロック状態（`ensure_open`）以外の確認が無い。パスワードや PIN も無い。
- 押印は、文書の署名、権限、読み取り専用を `stamp_refusal` で確かめ、承認を照合する。

## 2. STEP 116 の再現結果（要約）

製品の `seal_store.rs` を別プロセスから動かした結果である。

- 登録の消失、履歴の消失、削除した印影の復活、押印失敗の取り消しによる他人の行の消失が、決定的に起きた。
- 同時書き込みでは 20/20 で消えた。読み直しだけ（ロック無し）でも 20/20 で消えた。
- ファイルの破損と、利用者への通知は、どれも無かった。

## 3. 設計上の安全性要件

| ID | 要件 |
|---|---|
| R1 | 他プロセスの変更を消さない（登録、更新、削除、履歴） |
| R2 | 削除した印影を復活させない。別プロセスで削除・差し替えられた印影で、古い承認のまま押印させない |
| R3 | 監査記録を永続化できない場合、押印、注釈削除、Undo / Redo を成功扱いにしない |
| R4 | 監査記録を黙って消さない（上限での削除も、取り消しのための物理削除もしない） |
| R5 | 失敗した押印を成功と誤認させない。再試行で重複記録を作らない |
| R6 | 保存の失敗、中断、競合で、既存のファイルを壊さない。入力（下書き、仮置き、承認）を失わない |
| R7 | 旧版の書き込みで新しいデータを失わない。旧版の書き込みを検出し、保全する |
| R8 | 復号できないファイルを初期化しない、上書きしない、自動で復元しない |
| R9 | 移行は一方向で、元のファイルを暗号文のまま保全してから行う |
| R10 | 印影、平文、鍵をログに出さない |

## 4. SWSEAL2 スキーマ

### 4.1 ファイルの配置（同じフォルダ）

| ファイル | 役割 | 書き方 |
|---|---|---|
| `seals.v2.bin` | 新しいストア。印影と全監査履歴 | 原子的な置き換えだけ |
| `seals.bin.lock` | プロセス間ロック。空 | 作成だけ。書かない、消さない |
| `seals.bin` | 移行後は**墓標**（平文の 2 行、秘密は含まない） | `create_new` だけ。既存のものは置き換えない |
| `seals.bin.swseal1-<sha16>.bak` | 移行元の暗号文。バイト単位でそのまま | rename で移すだけ |
| `seals.bin.legacy-g<世代>-<sha16>.bak` | 移行後に旧版が書いた `SWSEAL1` を保全したもの | rename で移すだけ |

**別のファイル名にする理由**:
- 同じ `seals.bin` に `SWSEAL2` を書く方式では、移行前に `SWSEAL1` を読み込んだ旧版のプロセスが、後で同じ名前へ rename して、`SWSEAL2` を丸ごと置き換えてしまう。
- 新しいフィールドを足すだけでも、マジックを変えるだけでも、旧版の書き戻しは防げない。
- 名前を分ければ、旧版は `seals.v2.bin` を一切書かない。旧版の書き戻しは `seals.bin`（墓標）に当たるだけになり、新版はそれを検出して保全する（M2 で実証）。

### 4.2 バイト配置

`SWSEAL2\n`（8 バイト、平文）と DPAPI 暗号文（`CryptProtectData`、現在ユーザー、エントロピー無し。現行と同じ）。暗号化の範囲は平文 JSON の全体で、ヘッダーはマジックだけ。

### 4.3 平文 JSON

```json
{
  "schema": 2,
  "store_id": "store-<128bit hex>",
  "generation": 17,
  "migrated_from": {
    "format": "SWSEAL1",
    "source_sha256": "<移行元の暗号文ファイル全体の SHA-256>",
    "source_seals": 2,
    "source_events": 400,
    "backup": "seals.bin.swseal1-<sha16>.bak",
    "at": "2026-10-23 04:15:01 UTC"
  },
  "seals": [{
    "id": "seal-<128bit hex>",
    "revision": 3,
    "name": "…", "file": "…", "width": 64, "height": 64,
    "data": "<PNG base64>",
    "sha256": "<PNG の SHA-256>",
    "scale": 100.0,
    "effects": { "enabled": false }
  }],
  "deleted": [{ "id": "seal-…", "name": "…", "sha256": "…", "generation": 9 }],
  "events": [{
    "id": "ev-<128bit hex>",
    "seq": 17,
    "at": "… UTC",
    "kind": "use_prepared",
    "op_id": "op-<128bit hex>",
    "seal_id": "seal-…", "seal_name": "…",
    "image_sha256": "<押した PNG の SHA-256>",
    "file": "…", "page": 1,
    "note": { "processed": true, "angle_deg": 1.5, "fade": 10.0, "seed": 0, "rotation_mode": "random" }
  }]
}
```

`effects` は現行の `SealEffects` と同じ欄を持つ。`migrated_from` は移行したストアだけに入り、それ以外は `null` になる。

### 4.4 ID、世代、版

| 値 | 付与 | 規則 |
|---|---|---|
| `store_id` | 最初の書き込み（または移行）で 1 回 | 128 bit。`getrandom` 0.4 を使う（`ui-egui` の既存の直接依存。新しい依存は不要） |
| `generation` | 書き込みが成功するたびに +1 | 単調増加。ロックの中でだけ増やす |
| `seal.id` | 登録時 | 128 bit。同名の再登録は別の ID になる |
| `seal.revision` | 登録時 1。倍率、加工、画像の変更ごとに +1 | 楽観的な比較に使う |
| `event.id` | イベントの作成時 | 128 bit。一意 |
| `event.seq` | 書き込み時の `generation` | 移行で取り込んだ行は 1（順序は配列の順）。それ以外は一意で増加する |
| `op_id` | 承認スナップショットの作成時（1 回の押印の試み） | 128 bit。`SealApproval` と `SealUse` に持つ |

SHA-256 は、`stamps_ui.rs` の既存の `sha256_bytes` を共通の場所へ移して使う（新しい依存は不要）。

### 4.5 検証（読み込みのたびに、書き込みの前と後にも）

次の場合、ファイル全体を拒否してロック状態にする。ファイルは変えない。

1. マジックが `SWSEAL2\n` でない。
2. DPAPI で復号できない。暗号文の改ざんもここで失敗する（プロトタイプ I で、1 ビットの反転が失敗した）。
3. 平文が上限（案: 64 MiB）を超える。
4. JSON を解析できない。
5. `schema != 2`。**未知の版は拒否する**（将来の版は `schema` を上げ、旧い読み手は必ず拒否する）。
6. `store_id` が空なのに `generation > 0`。
7. 印影の ID または名前が空、または重複。`revision == 0`。`sha256` が `data` と合わない。8 件を超える。
8. `deleted` の ID が `seals` に残っている。
9. イベントの ID が空、または重複。`seq` が減少する。`seq > generation`。
10. `kind` が既知の一覧に無い。

同じ版の中の未知の欄は、読み捨てずに拒否するか保持するかを決める必要がある。推奨は、v1.0 では `deny_unknown_fields` で拒否し、欄を足すときは `schema` を上げる方法（19 節）。

### 4.6 旧版からの見え方（実証）

旧版（`c740330` の `seal_store.rs` そのもの）で試した結果:
- 墓標の `seals.bin` を開くと、ロック状態になる。登録は拒否され、ファイルは変わらない。
- `seals.v2.bin` を直接開いても同じだった（M1）。
- 旧版の文言は「印影ファイルを復号できませんでした」なので、リリースノートで説明する。

## 5. プロセス間排他

### 5.1 手段

- `std::fs::File::try_lock`（Rust 1.89 から安定。現行の 1.96 で使えることを、ビルドと実行で確かめた。Windows では `LockFileEx` の排他ロック）。
- 依存の追加も `unsafe` も要らない。
- `crates/platform` に `lock_with_timeout(path, timeout)` を置き、`staging` と並べる。

### 5.2 規則

- ロック対象は `seals.bin.lock`（`create(true).truncate(false)` で開く。内容は書かない。消さない）。`seals.v2.bin` は rename で置き換わるので、ロックの対象にしない。
- ロックの保持は、1 回の操作（読み込みから読み直しまで）の間だけ。UI の操作やダイアログをまたいで持たない。
- 待ち時間の上限は 3 秒（初期値）。`try_lock` と 25 ms の待機を繰り返す。
  - 時間切れなら操作を適用しない。入力は保持する（12 節）。
- 異常終了: OS がハンドルを閉じて解放する。
  - 実証: ロックを持ったまま `exit(0)` しても、`abort()` しても、もう一方は 0 ms で取得できた。
  - ロックファイルは 0 バイトのまま残った。

### 5.3 パスの別名

| 別名 | 結果 |
|---|---|
| 大文字・小文字、`/` と `\` の違い | 同じロックで止まった（実証） |
| ディレクトリのジャンクション | 同じロックで止まった（実証）。ロックファイルが、実体の同じフォルダにあるため |
| フォルダへのシンボリックリンク | 同じ理由で同じロックになると考えられる（未実証。作成に権限が要る） |
| `seals.v2.bin` そのもののシンボリックリンク、ハードリンク | 別フォルダにあると別のロックになる。ただし書き込みは rename で、そのフォルダの名前だけを置き換えるので、最初の書き込みで別々のファイルに分かれる。同じファイルを奪い合う破損ではなく、古い写しが残る状態になる |

対策:
- ストアのフォルダは `canonicalize` して扱う。
- `seals.v2.bin` がシンボリックリンクなら拒否する（`symlink_metadata`）。
- ハードリンクの検出は、安定版の標準 API に無いので、保証の対象外にする（16 節）。

## 6. 操作単位の更新モデル

**プロセスが持っているストア全体を書き戻す方式は廃止する。** メモリ上の内容は、表示と承認のための「最後に見た状態」に過ぎない。

```text
apply(op):
  1 ロック取得（≤3 秒）──失敗→ Err(Busy)。適用しない
  2 open(): seals.v2.bin を読む。無ければ移行か新規（11 節）。seals.bin の状態を確認（墓標、旧版の書き込み）
  3 検証（4.5）──失敗→ Err(Locked)。何も書かない
  4 op(&mut body): 対象の存在、revision、sha を照合し、依頼された操作だけを適用。イベントを追加
     変更が無ければ（冪等な再試行）書かずに Ok
  5 generation += 1。新しいイベントの seq = generation
  6 検証（4.5）
  7 一時ファイルへ書き、sync_all、rename（既存の write_atomically）
  8 読み直して復号し、body と完全一致することを確かめる──不一致→ Err(Verify)
  9 墓標を確認（無ければ create_new）
 10 ロック解放（スコープの終わり）
 11 呼び出し側: メモリを、書いた body に置き換える（他プロセスの変更も、ここで画面に入る）
```

自動マージは、操作の再適用（最新の内容に 1 つの操作を適用する）に限る。安全性は次のとおり。

- 履歴の追加は追記だけなので、他の行に影響しない。
- 印影の変更は、`revision` と `sha256` が一致する場合にだけ適用する。
- スナップショットどうしのマージはしない。

## 7. 印影の更新・削除の競合対策

| 操作 | 照合 | 競合時 |
|---|---|---|
| 登録 | 同名が無いこと。8 件未満 | 「同じ名前の理事長印が既にあります」。下書きは保持 |
| 倍率・加工の変更 | `seal.id` が存在し、`revision` が画面の値と一致 | 「ほかのウィンドウで変更されました。最新の内容を表示しました。」。変更は適用せず、画面を最新にする |
| 削除 | 同上 | 既に無い場合: 「既に削除されています」。変わっている場合: 拒否して最新を表示 |

- 削除は `seals` から外し、`deleted` に墓標（id、name、sha、generation）を残す。イベントは `seal_deleted`。削除した印影は、どの経路でも復活しない（プロトタイプ K）。
- UI の選択（`QuickTool::ChairmanSeal`）は、添字ではなく `seal.id` で持つ。

## 8. 承認と押印の整合性

- `SealApproval` に、`op_id`、`seal_id`、`seal_revision`、`seal_sha256`（登録 PNG）を追加する。既存の `sha256`（押す PNG）、`doc`、`page`、`rect`、`opacity`、`preview_gen` は維持する。
- 押印の順序:
  1. 既存の照合（承認スナップショットと、押す PNG の SHA-256）
  2. `apply(use_prepared)`: ロックの中で、`seal_id` が存在し、`revision` と `sha256` が承認時のものと一致することを確かめる。消えていた、または変わっていた場合は押印しない。承認を捨て、「承認後に印影が変更または削除されたため、押印しませんでした。もう一度確認してください。」を表示する。
  3. `apply_edit(AddCustomStamp)`
  4. 成功したら `apply(use_committed)`。失敗したら `apply(use_cancelled)`。
- `use_committed` を書けなかった場合（ロックの時間切れなど）は、R3 に従い、文書の押印を Undo で戻す。そのうえで `use_cancelled` を試みる。
  - これも書けなければ、`use_prepared` だけが残る。表示上は「未完了」とし、押印されていない可能性があることを示す。
  - `op_id` をメモリに残し、次に書けたとき、冪等に結果を記録する。
- プロトタイプ K での実証:
  - 別プロセスで削除された Y を使おうとすると、拒否された。
  - 削除のあと同名で再登録された X も、拒否された。
  - 最新の内容を読み直した後は、押印できた。

## 9. 監査履歴の保存方式比較

計測条件: プロトタイプ P。256×256 のノイズ PNG（約 139 KB）を 8 件。1 回の操作（ロック、読み込み、復号、検証、追加、暗号化、書き込み、読み直し）の時間。

| イベント数 | ファイル | 1 操作 |
|---|---|---|
| 400 | 1.66 MB | 177〜642 ms |
| 10,000 | 5.83 MB | 0.7〜1.0 秒 |
| 50,000 | 23.3 MB | 2.5〜3.8 秒（ロックの待ち時間 3 秒を超えうる） |

| 案 | 原子性 | 長期保持 | 実装と検証 | 評価 |
|---|---|---|---|---|
| A: SWSEAL2 内に無制限 | 1 ファイルの置き換えだけ。押印と記録の不整合が起きない | 時間とサイズが行数に比例する。1 万行で約 1 秒 | 小 | **v1.0 に推奨** |
| B: 暗号化した別のイベントログ | 2 ファイルの更新になる。順序と復旧の設計が要る。追記中の破損への対策が要る | 良い | 中〜大 | 単独では採らない |
| C: 世代付きスナップショットと、封じた履歴の区画 | 区画を先に書き、本体の参照を原子的に切り替えれば保てる | 良い | 大 | v1.1 以降の拡張として設計を残す |

**推奨: 案 A**（v1.0.0）。理由:
- 押印、記録、取り消しが、すべて 1 回の原子的な置き換えで済む。
- 「押印だけ成功して記録が欠ける」状態が、構造上起きない。
- 検証が最も単純である。

利用頻度の試算（仮定。要確認）: 月 20 回の押印で、1 回あたり準備と結果の 2 行なら、年 480 行になる。1 万行まで約 20 年かかる。

上限の扱い:
- 黙って消すことはしない。
- 目安を超えたら警告する。例: 10,000 イベント、または平文 8 MiB。
- 平文の上限（案: 64 MiB）に達したら、新しい押印を拒否し、理由を表示する（業務は止まるが、記録は消えない）。

案 C の拡張（v1.1 以降）:
- 古いイベントを、封じた区画 `seals.audit-<n>.bin`（DPAPI 暗号化、書き換え不可）へ移す。
- 本体には、区画の `sha256`、イベント数、最初と最後の `seq` を記録する。
- 区画を書いて読み直し、確認した後で、本体を原子的に置き換える。途中で止まっても、参照されない区画が残るだけで、記録は消えない。

## 10. 取消イベント

| `kind` | 意味 | 付与 |
|---|---|---|
| `seal_registered` / `seal_updated` / `seal_deleted` | 印影の管理 | `seal_id` |
| `use_prepared` | 承認を照合し、押印に入る直前 | `op_id`（承認ごとに新規）、`seal_id`、`image_sha256`、`file`、`page`、`note` |
| `use_committed` | 文書（作業中の PDF）に入った。保存や発行の意味ではない（現行の注記を維持） | 同じ `op_id` |
| `use_cancelled` | 文書に入らなかった（適用の失敗、記録の失敗による取り消し） | 同じ `op_id` |
| `use_undone` / `use_redone` / `use_removed` / `use_removal_undone` | 現行の `undone`、`redone`、`removed`、`removal-undone` に当たる | 元の押印の `op_id`（`SealUse` に持つ） |
| `legacy:<旧 event>` | 移行で取り込んだ SWSEAL1 の行 | `seq = 1`、`op_id` は空 |
| `migrated` | 移行の記録 | `note` に移行元の sha とバックアップ名 |
| `legacy_write_detected` | 移行後に旧版が `seals.bin` を書いたことを検出し、保全した | `note` に保全ファイルの名前と sha |

保証の仕組み:
- 他の行を消さない: 物理的な削除をやめ、追記だけにする。
- 自分の操作だけを特定する: `op_id` で引く。
- 失敗を成功と誤認させない: `use_committed` が無い押印は、成功と表示しない。
- 時系列: `seq` と配列の順が、書き込みの順を表す。
- 重複を作らない: `(op_id, kind)` が既にあれば、書かずに `Ok` を返す（冪等）。

プロトタイプ K での実証:
- 同じ準備の再試行で、記録は 1 件のまま。
- 取り消しの再試行で、重複は無かった。
- 取り消した押印の確定は拒否された。
- B の取り消しが A の記録に影響しなかった。

## 11. データ移行（SWSEAL1 → SWSEAL2、一方向）

### 11.1 前提

- 移行は自動で始めない。理事長印を初めて使うとき（一覧の表示、登録、押印）に、確認を出す。
  - 「理事長印のデータを新しい形式に移します。ほかの SwiftPDF（旧版を含む）をすべて閉じてから［移行する］を押してください。元のファイルは、そのまま保管します。旧版では理事長印を使えなくなります。」
- 拒否された場合は延期する。理事長印は使えない状態（ロック状態の表示）のままにし、ほかの機能は使える。
- 旧版の終了を完全に確かめる手段は無いので、確認は補助と位置付ける。安全性は 11.3 の「何も上書きしない手順」で保証する。
  - 補助として、単一インスタンス用ソケットへ接続を試み、応答があれば移行を延期する（同じセッションの、v0.8 以降の一部だけ。要確認）。
  - 補助として、MSI の CloseApplications を使う（要確認）。

### 11.2 手順（すべてロックの中）

```text
状態0: seals.bin = SWSEAL1、seals.v2.bin なし
 1 ロック取得
 2 seals.bin を読み、src_sha を計算
 3 現行の decode_file で復号・検証（400 行をすべて保持）──失敗→ 中止（何も書かない）
 4 SWSEAL2 本体を作る（印影に id、revision=1、sha。行は legacy:*、seq=1。migrated 行。migrated_from）
 5 seals.v2.bin を原子的に書き、読み直して確認           ──状態1: 両方あり
 6 seals.bin を seals.bin.swseal1-<sha16>.bak へ rename（既存名なら中止）──状態2: bak と v2
 7 bak を読み、sha == src_sha を確認
     違う → 手順 2〜5 の間に旧版が書いた。bak から作り直して v2 を書き直す（新しい sha 名へ rename）
 8 墓標 seals.bin を create_new（既にあれば、旧版が直後に書いた → 次の open で検出）──状態3: 完了
 9 ロック解放。UI に「移行しました。元のファイルは <bak> に保管しています。」を表示
```

**新版は、移行の手順で既存のファイルを一度も置き換えない。** 使う操作は、rename での移動、`create_new`、v2 の新規作成だけである。

### 11.3 障害時の評価（プロトタイプ M）

| 障害 | 状態 | 次の起動 | 実証 |
|---|---|---|---|
| バックアップの作成（rename）に失敗 | 状態 1（v2 あり、`seals.bin` そのまま） | `seals.bin` の sha == `source_sha256` で、バックアップ名が無い → 手順 6 から再開 | M4b と同じ経路 |
| 容量不足、暗号化の失敗、v2 の書き込み失敗 | 状態 0 のまま | 最初からやり直す | M4a: `seals.bin` は変わらず、再起動で移行は 1 回だけ |
| ロックの取得に失敗 | 状態 0 | 延期 | L1 |
| DPAPI で復号できない | 状態 0 | 移行しない。ロック状態。ファイルはそのまま | 現行と同じ |
| v2 の書き込み後に中断 | 状態 1 | 手順 6 から再開 | M4b: バックアップ == 元のバイト、移行の記録 1 件 |
| rename の後に中断 | 状態 2（`seals.bin` が無い） | 墓標を作るだけ | M4c |
| 移行後の検証に失敗 | v2 を読み直せない | v2 があって不正 → ロック状態。`seals.bin` は状態 1 のまま残る | 方針 |
| 旧版が既に起動していた（移行の途中で書いた） | 手順 7 で検出 | 新しい内容で作り直す | M3: 旧版の行が v2 に入った |
| 旧版による遅延書き戻し（移行の後） | 旧版が墓標を `SWSEAL1` で置き換える。**v2 は無傷** | 次の操作で検出し、`seals.bin.legacy-*.bak` へ移し、`legacy_write_detected` を記録し、墓標を作り直す | M2: v2 は変わらず、保全ファイルは旧版で開ける |
| v2 が無く、墓標がある | 手作業で消したなど | **新しく作らない**。ロック状態にし、バックアップの場所を案内する | M5 |

- 遅延書き戻しで旧版が記録した行は、保全ファイルに残るが、v2 へは自動で取り込まない（判断事項）。
- 利用者には「旧版の SwiftPDF が理事長印のファイルを書き換えました。旧版を終了してください。旧版の記録は <ファイル> に保管しました。」と知らせる。

## 12. バックアップと復元

- **移行のバックアップ**: 元のファイルを rename で移すので、暗号文のまま、バイト単位で同じである（M1: バイト一致、sha 一致）。複製を作らないので、容量不足でバックアップだけ失敗することも無い。
- **保全ファイル**（`legacy-*.bak`）: 旧版が書くたびに 1 つできる。
- **保持期間**: 自動では消さない。不要になったら、利用者が手作業で消す（説明書に書く）。
- **権限**: フォルダの ACL を引き継ぐ。`%LOCALAPPDATA%` は既定で本人だけ。ポータブルの `Data` は、置いたフォルダの権限次第である。
- **復元**: 自動では行わない（R8）。手作業の手順を説明書に書く。
  - SwiftPDF をすべて終了する。
  - `seals.v2.bin` を別名に退避する。
  - `.bak` を `seals.bin` にする。
  - 旧版を使うか、新版で再び移行する。
- **古いバックアップでの上書き事故**:
  - `seals.bin` に古い `.bak` を戻した場合: v2 があるので「旧版の書き込み」として保全され、v2 は上書きされない。
  - `seals.v2.bin` を古い写しに戻した場合: 世代の巻き戻りは、本体だけでは検出できない。案として、`seals.v2.gen`（`store_id` と最大世代を DPAPI で保護）を併用し、本体の世代が小さければ警告する（判断事項。補助であり、原子性には関与しない）。

## 13. DPAPI とアクセス制御

| 状況 | 結果 |
|---|---|
| 同じユーザー、同じ PC | 復号できる（パスワードを変えた後も） |
| 別ユーザー、別 PC、Windows の再インストール後 | 復号できない（再インストール後は要実機確認）。ロック状態になり、初期化も上書きもしない。移行もしない |
| バックアップ | 暗号文のままなので、同じ条件でだけ復号できる |
| 改ざん | 暗号文の改ざんは、復号の失敗として検出する（I）。同じユーザーとして動くプログラムによる正規の再暗号化は、区別できない |
| 管理者 | このユーザーとして動けば、読み書きできる |

## 14. 障害復旧と、保存成功の条件

保存（`apply`）が `Ok` を返すのは、次のすべてを満たしたときだけである。

1. ロックを取得した。
2. 最新の内容を読み、検証した。
3. 操作の照合に通った。
4. 書き込み、`sync_all`、rename が成功した。
5. 読み直して完全に一致した。

墓標の作成だけに失敗した場合は、データは保存済みなので、成功として警告を出す。

| 障害 | 結果 | 入力 | 利用者への通知（案） |
|---|---|---|---|
| ロックの時間切れ | 適用しない | 保持 | 「ほかの SwiftPDF が理事長印のデータを使用中です。少し待ってからもう一度お試しください。」 |
| 容量不足、一時ファイルの作成失敗、rename の失敗 | 既存のファイルはそのまま。一時ファイルは削除 | 保持 | 「理事長印のデータを保存できませんでした。空き容量を確認してください。押印はしていません。」 |
| 暗号化の失敗 | 同上 | 保持 | 同上 |
| 復号の失敗、検証の失敗 | ロック状態。何も書かない | 保持 | 「理事長印のファイルを読めません。ファイルはそのままにしてあります。」と、保存場所 |
| 保存後の検証に失敗 | `Err`。ファイルは新しい内容の可能性がある | 保持 | 再試行は冪等なので、重複しない |
| 監査イベントの追加に失敗 | 押印、削除、Undo / Redo を成功扱いにしない（8 節） | 保持 | 現行の文言を維持 |
| 移行の途中で停止 | 11.3 のとおり、次の起動で再開 | — | — |
| 復旧後の重複 | `(op_id, kind)` の冪等性で、作らない | — | — |

## 16. 保証範囲と対象外

| 対象 | 扱い |
|---|---|
| 同一ユーザーの複数プロセス（新版どうし） | **保証する**（ロックと操作単位の更新） |
| 旧版との同時利用 | **データを失わないことを保証する**（別名、墓標、保全、検出）。旧版が移行後に記録した行は、v2 に自動で入らない。**ファイルロックだけでは、旧版や外部プログラムによる書き換えは防げない** |
| ポータブル版との同時利用 | 同じ `Data` なら同じロックになり、保証する。別の `Data` なら別のストアになる（共有しない） |
| 別の Windows ユーザー | 復号できない（DPAPI）。共有の保証はしない |
| ネットワーク共有 | 対象外。SMB でもロックは効く見込みだが、未検証 |
| OneDrive などの同期フォルダ | 対象外。同期による置き換えと競合は、検出も防止もしない。ポータブルの `Data` が同期フォルダにあれば警告することを推奨 |
| ジャンクション、シンボリックリンク | フォルダ単位なら同じロックになる。ファイル単位のリンクは拒否するか、対象外 |
| ハードリンク | 対象外（分岐するだけで、破損はしない） |
| 手動でのコピーや復元 | 12 節の範囲で検出と保全をする。完全ではない |
| 管理者権限による直接の改変 | 対象外 |

## 17. 残存リスク

1. **旧版が移行後に記録した押印**は、保全ファイルにだけ残る。監査記録が 2 か所に分かれる。検出して通知はするが、旧版の終了は利用者に頼る。
2. **履歴の量**: 5 万行で 1 操作が 3 秒を超えうる。10 年規模では問題にならない見込みだが、利用頻度の仮定は要確認。案 C の拡張が必要になる時期がある。
3. **UI の停止**: ロックの待ちと保存は UI スレッドで行う想定で、最大で約 3 秒止まりうる。
4. 世代の巻き戻り（v2 の古い写しの復元）は、補助ファイルを入れない限り検出できない。
5. 同じユーザーによる改ざんは防げない。
6. 旧版の文言「復号できませんでした」は、移行済みの状態を誤解させる。
7. 単一インスタンス用ソケットによる旧版の検出は、一部の起動にしか効かない。
