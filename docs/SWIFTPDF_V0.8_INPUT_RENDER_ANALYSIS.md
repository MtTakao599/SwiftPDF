## 5. 描画・テストハーネスの共有資源

`egui_kittest` 0.36.2 の `default_wgpu_setup` は、アダプタを `DeviceType::Cpu` 優先で選ぶ。Windows ではこれが WARP で、実装は `d3d10warp.dll` にある。各ハーネスが `WgpuTestRenderer::new` で自分の `Device` と `Queue` を作る。テスト間でテクスチャを共有するコードは無い。

製品側の `unsafe` は禁止されている。`ui-egui` の `OnceLock`（フォント、i18n、ポータブル設定）は、落ちたモジュールと一致しない。

デバイスの破棄はハーネスの drop に任されている。3件同時の実行は、どれかが `ok` を出す前にプロセスごと落ちた。終了処理だけが原因とは言えない。標準出力がクラッシュで欠ける可能性はある。

## 6. v0.7.0 との比較

`content.rs` と `Cargo.lock` は両版で同じ。3件を同時に始めると、両方とも `0xc0000005`、同じ DLL、同じオフセット `0x7b55f` で落ちる。

STEP 96-B で v0.7.0 の14件・8スレッドが2回成功し、v0.8.0 が2回落ちた差は残る。ただし、描画する3件だけを同時に始めると v0.7.0 も落ちる。8スレッドの差は、v0.8.0 のフレームが重く、3件の `render` が重なりやすい、で説明できる。`anchored_scroll` が WARP を呼ぶ根拠は無い。

判定: テストハーネスが、プロセス内で複数の WARP デバイスを同時に作る問題。v0.8.0 固有の描画回帰としては確定しない。GPU 資源の競合は、製品の共有テクスチャではなく、テストごとのデバイスが WARP 上で同時に動くこと。UI のスレッド安全性を、製品コードの1行には結び付けられない。

## 7. Escape 入力の処理経路

1フレームの順は `PdfCraftApp::update` である。

1. `shortcuts`。`front_prompt()` があるときはここで戻る。したがって `canvas::shortcuts` の Escape（選択解除、検索を閉じる、カメラ中止）はダイアログ中には動かない。
2. `document_area`。追加テキスト、段落、フォーム、コメントの編集欄が、ここで `key_pressed(Escape)` を読む。
3. `dialogs::show`。前面のダイアログだけが Escape を消費して閉じる。

`key_pressed` は、先に `consume_key` されていても真のままである。さらに編集欄はダイアログより前に動く。消費の有無では編集欄を止められない。

`document_area` は `unobstructed = !modal_open()` をポインタ操作には使う。編集欄の Escape には渡していない。

| 箇所 | 条件 | 最前面の確認 | Escape の効果 |
|---|---|---|---|
| `lib.rs` `shortcuts` | プロンプトが無いときだけ先へ進む | あり | 文書ショートカット。ダイアログ中は動かない |
| `canvas.rs` `shortcuts` 2231 | 上の関数からだけ | 上に従う | 選択、検索、カメラ |

## 8. Escape 問題の再現状況

実行した UI は無い。同じフレームで両方が動くことは、呼び出し順と `key_pressed` の定義から決まる。ダイアログを開いたあと下書きが残っていることが条件である。

- 前面がフォーカスを奪わない（設定、印影効果、承認画面でテキスト欄へ `request_focus` していない）: 下書きは残る。Escape 1回で、ダイアログが閉じ、追加テキストの下書きが捨てられる。
- パスワード画面は毎フレーム `request_focus` する。追加テキスト側は、印刷とスタンプ以外ではフォーカスを失うと下書きを確定する（`content_ui.rs` 772、呼び出しは `canvas.rs` 3826）。パスワードを開いた時点で、Escape より前に下書きが編集として入る経路がある。どのダイアログがフォーカスを奪うかは、GUI で見ていない。

既存テスト `a_dialog_above_a_save_prompt_keeps_the_prompt` は、保存確認の背後に編集欄が無い。前面のダイアログと保存確認の役割分担は通っている。編集欄との同時操作はテストが無い。

実機で見る手順（架空の PDF）:

1. 新規 PDF で文字を置き、確定しない。
2. 設定、または印影効果を開く。ページはクリックしない。
3. Escape を1回押す。
4. ダイアログだけが閉じ、入力中の文字が残るのが期待。現状のコードは同じフレームで下書きを捨てる。

## 9. 製品への影響

並列クラッシュ: デスクトップは UI スレッドが1つで、デバイスも1つである。利用者が同じプロセスで WARP デバイスを複数作る経路は、この調査では見つかっていない。落ちるのは `content` のヘッドレス描画を並列にしたとき。1スレッドでは14件成功する。製品の保存や押印が壊れる結果は出ていない。

Escape:

- 未確定の追加テキストは、前面のダイアログを閉じる Escape で捨てられる。確定済みの文字は残る。Undo は増えない。
- 段落の未適用の修正も、同じ Escape で捨てられる。
- 承認画面の Escape は、元から承認を捨てて押印しない。テキスト下書きが別に開いていれば、それも捨てる。押印が2回走る経路は無い（Escape は `commit_stamp_place` を呼ばない）。
- 保存確認の Escape は保存を始めず、閉じるのを取り消す。その同じキーが下書きも捨てる。
- パスワード画面は、フォーカス移動で下書きを確定してしまう可能性がある。これは Escape とは別の穴で、GUI では未確認。

未確定テキストが消える方が、WARP のテストクラッシュより利用者への影響が大きい。

## 10. 修正案と優先順位

実装はしていない。

### A. 並列クラッシュ

| 案 | 規模 | 安全性 | 副作用 | 回帰テスト |
|---|---|---|---|---|
| `content` を `--test-threads=1` で実行する | 実行条件だけ | デバイスが1つになる。3件同時の落ち方は止まる | CI がそのターゲットだけ遅くなる | 14件が1スレッドで成功すること。3件同時は再現用に1回だけ |
| 描画読み戻しの3件だけ直列にする | テストの起動方法 | 上と同じ | 他の UI テストの並列は残る | 上に加え、3件のフィルタ実行 |
| テスト用レンダラを wgpu 以外にする | 依存の設定 | WARP を使わなければこの DLL では落ちない | ピクセル比較の結果が変わる | ドラッグ中のインクのテスト |
| 製品の `canvas.rs` を直す | 製品 | 根拠が無い | ズームの挙動を変える | 不要 |

推奨は1番。製品の共有資源は無いので、デバイスの共有を直す箇所は製品に無い。

### B. Escape

| 案 | 規模 | 安全性 | 副作用 | 回帰テスト |
|---|---|---|---|---|
| `document_area` の `unobstructed` を、追加テキスト・段落・フォーム・コメントの Escape に渡す | 呼び出し引数。判定は既存の `modal_open` | 前面があるとき、下書きは残る。ダイアログは今どおり閉じる | ダイアログ中の Escape では編集を取り消せなくなる。それが目的 | 下書きを開いたまま設定を開き、Escape で下書きが残ること。ダイアログが無いときの Escape は今どおり捨てること |
| フォーカスを失っても、`modal_open` のあいだは下書きを確定しない | 印刷ダイアログ向けの例外を、すべてのプロンプトへ広げる | パスワード画面がフォーカスを奪っても、未確定文字が勝手に編集へ入らない | ダイアログを開いただけでは文字が確定しなくなる | 印刷で既にある「フォーカスを失っても確定しない」と同じ形 |
| キー処理を `shortcuts` へ移す | 大きい | テキスト欄は `egui_wants_keyboard_input` が真なので、移すと Escape が届かなくなる | ダイアログが無いときの取り消しが壊れる | 広い |

推奨は1番、その次に2番。1番だけでは、パスワード画面が開いた瞬間の確定は残る。

優先順:

1. Escape で未確定テキストを捨てない（案 B-1、続けて B-2）。利用者の入力が消える。v0.8.0 の「前面だけが Escape を取る」を完成させる修正で、コミット前がよい。
2. `content` の描画テストを1スレッドにする（案 A-1）。製品クラッシュではない。v0.7.0 でも3件同時なら落ちる。コミットを止める理由にはしない。8スレッドの成功を、リリース条件にしない。
3. アウトラインの名前変更と検索バーは、同じ `key_pressed` なので、B-1 のあとで同じガードを足す。ページ本文は消えない。

## 11. v0.8.0 のコミット可否

WARP のアクセス違反は、v0.8.0 のズーム修正が原因だと確定しない。同じ3件を同時に動かすと v0.7.0 も同じオフセットで落ちる。このクラッシュだけを理由に、製品差分のコミットを止める必要は無い。ただし `content` を8スレッドで緑とは扱えない。

Escape は、STEP 93 がダイアログ同士とショートカットには入れたガードが、ページ編集欄に届いていない。未確定の文字が消える。この穴を残したまま「前面だけがキーを取る」とは言えない。コミット前に、編集欄の Escape を `modal_open` で止める修正を別ステップで入れるのがよい。今回の調査では入れていない。
