## 2. xref 再構成 PDF の判定方式

`assess` は次の順に判定する。

1. `revisions()` が空で `repair_log()` が空でないとき（xref を再構成した場合）は、`raw_names_clear(cos.bytes())` を実行する。拒否の対象になる名前が 1 つでもあれば `Indeterminate` にして、回転を拒否する。
2. 通常の検査 `assess_current` を行う。対象は次のとおり:
   - フォームの `/FT /Sig` と `/V`
   - `/Perms` の `/DocMDP`、`/UR`、`/UR3`
   - 全オブジェクトの署名辞書、`/ByteRange`、`/SubFilter`
   - トレーラーと `/Encrypt`
3. 古い改訂を最大 64 個、`open_with_same_credentials` で開いて同じ検査をする。開けない改訂や再構成された改訂は `Indeterminate` とする。

生バイト列の検査の性質は次のとおりである。

- **範囲**: `cos.bytes()`、つまりファイル全体（ヘッダーの前も含む）を先頭から最後まで調べる。
- **名前の区切り**: 空白文字（`\0 \t \n \f \r` と空白）と区切り文字（`( ) < > [ ] { } / %`）。cos の字句解析器と同じ集合であることをコードで確認した。
- **拒否する名前**:
  - `#` を含む名前（エスケープ）
  - `Sig` で始まる名前
  - `ByteRange`、`SubFilter`、`Perms`、`DocMDP`、`UR`、`UR3`、`DocTimeStamp`、`TransformParams`、`ObjStm`、`Encrypt`（完全一致）
- **文字列、コメント、ストリームと辞書キーの区別**: しない。どこに現れた名前も同じに扱い、拒否する側（安全側）に倒す。
- **検査を通った場合**: 必ず手順 2 と 3 に進む。生バイト列の検査は「拒否を増やす」ためだけにあり、単独で「署名なし」とは判定しない。

## 3. 名前エスケープ・圧縮・暗号化の評価

- **`#xx` エスケープ**: cos は名前の本体で `#` と 16 進 2 桁を 1 バイトに戻す（`name_body`）。ほかのエスケープはない。生の検査は `#` を含む名前をすべて拒否する。したがって、エスケープで綴った `/Byte#52ange` や `/Sub#46ilter` は生の検査で拒否される。
- **cos にとっての等価性**: `#` を含まない名前では、cos が読む名前と生のバイト列がバイト単位で一致する（区切りの集合が同じため）。cos の読み方では、署名名がすり抜ける余地はない。
- **圧縮**:
  - 再構成のとき cos がたどる圧縮データは、`/Type` がそのままの名前 `/ObjStm` であるストリームの中身だけである（`reconstruct` 1866〜1876 行）。生の検査は `/ObjStm` を拒否する。
  - そのほかの圧縮ストリームの中身は、cos がオブジェクトとして読むことはない。
  - 実測: cos が書いた圧縮オブジェクトストリームに署名辞書を入れ、xref を壊した。生のバイト列には `/Sig` が現れないが、`/ObjStm` で拒否された。生の検査を止めても、通常の検査が展開後の署名辞書を見つけて拒否した。
- **暗号化**:
  - 名前は暗号化されない。
  - 再構成 PDF で `/Encrypt` を含むものは、生の検査で拒否する。
  - 正常な xref を持つ暗号化 PDF では、通常の検査が復号後のオブジェクトを調べる。

## 5. 見逃し・誤検出の有無

### 見逃し（新しい安全上の問題）

**xref の解釈が読み手によって分かれるファイルで、cos から見えない署名を見逃す。** この問題は STEP 110 の変更ではなく、STEP 105 以来の通常経路にある。探索コードは `step111\rotate_security_gap_probe.rs`、結果は `gap-probe.txt` と `gap-probe-classic.txt` にある。

| 再現 | cos の解釈 | 結果 |
|---|---|---|
| ハイブリッド: 表は 3 番と 7 番を無害な辞書に置く。`/XRefStm` は同じ番号を `/ObjStm` 内の署名フィールド（`/FT /Sig /V 7 0 R`）と署名辞書に置く | 改訂 1、修復なし、`xref_oddities` = 2 件。3 番は `/FT /Tx` | **回転可** |
| 同じファイルで `/XRefStm` を読めない位置にする | 改訂 1、`repair_log` に「hybrid /XRefStm unreadable」、食い違い 0 件 | **回転可** |
| 通常の表だけで、1 つの区画に 3 番と 7 番を 2 回ずつ載せる（前は無害、後は署名） | 改訂 1、`xref_oddities` = 2 件 | **回転可** |

- 3 ケースとも `is_signed` は false だった。
- cos の `xref_oddities` の説明には「別の読み手（ページ描画も含む）はこちらを採るかもしれず、同じ番号に別のオブジェクトを見ることがある」とある。ガードはこの情報を見ていない。
- 生の検査は `revisions()` が空のとき（完全な再構成）だけに働く。改訂が残る部分的な修復や食い違いには使われない。
- **影響**: 回転は新しいファイルへの別名保存だけなので、原本は壊れない。ただし、別の読み手が署名ありと見る文書を、回転した写しとして書き出せてしまう。「未署名と確認できないものは回転しない」という設計に反する。

### 生の検査に残る理論上の弱点（cos 以外の読み手が前提）

- 完全一致で比べる名前（`ByteRange`、`Perms`、`DocMDP` など）は、名前の区切りが cos と違う読み手にとってだけ、すり抜ける余地がある。たとえば 0x0B を区切りとみなす読み手である。
  - 署名フィールドに必要な `/Sig` は前方一致で拒否するので、この影響を受けない。
- `/Type /ObjStm` を持たない圧縮ストリームを、本文中の xref ストリームを使ってオブジェクトストリームとして読む寛容な読み手には、再構成 PDF の中身が見える。cos は再構成時に本文中の xref ストリームを使わない。

### 誤検出

再構成 PDF では次を拒否する。いずれも意図したもので、安全側である:

- `#` を含む名前
- 文字列やコメントの中の署名名
- 空の `/Perms`
- `/Encrypt`
- `/ObjStm`

## 6. 増分改訂と旧改訂の検査

- 正常な xref: 古い改訂を最大 64 個、それぞれの終わりまでのバイト列として開き直して検査する。後の改訂で解放した署名辞書は拒否された（通常と暗号化の両方）。
- 65 個以上の改訂は判定不能として拒否する。これは STEP 106 のテストで確認済み。
- 最新の xref が壊れて再構成になった場合は、全改訂のバイト列が生の検査の対象になる。古い改訂の署名辞書は拒否された。
- 古い改訂そのものが再構成になる場合は、拒否する。
- 限界: 古い改訂の中に §5 の食い違いがあっても、同じ理由で見逃す。

## 7. 暗号化 PDF の認証情報の扱い

- `open_with_same_credentials` は、今の文書の `/Encrypt` と `/ID` が一致するときだけ、認証済みのファイル鍵を使う。パスワードは受け取らず、保持もしない。
- 合成テストの結果:
  - 暗号化して改訂が 1 つまたは 3 つで、署名がない PDF は回転できた。
  - 古い改訂に署名辞書が残る暗号化 PDF は拒否された。
  - 古い改訂が今と違う `/ID` を持つ（認証情報が異なる）PDF は拒否された。その古い改訂は単独ならパスワードで開ける。拒否の理由が認証情報の不一致そのものであることを、テストで確認した。
  - パスワードが違う場合や、ない場合は、開くこと自体ができない。
- 情報漏えいについて:
  - ガードの本番コードは、ログ出力、書式化、修復ログへの追記を一切しない。
  - cos の `Credentials` には `Debug` がなく、表示されない。
  - 古い改訂を開いた文書は、ループごとに破棄される。
  - 拒否時のメッセージは固定文だけである。
  - テストのパスワード `pw` は合成データの固定値で、どのログにも出力していない。
- 読み取りに失敗した改訂は、未署名として扱わない（`Indeterminate`）。

## 13. xref 再構成 PDF を許可するか、一律拒否するかの推奨

| | 許可方式（STEP 110） | 一律拒否方式（STEP 106） |
|---|---|---|
| 安全性の説明 | cos については、すべてのバイトを調べるという根拠で説明できる。cos 以外の読み手には §5 の弱点が残る | 「読み手の解釈が分かれうるファイルは回転しない」と、1 文で説明できる |
| 利便性 | 壊れているが署名のない PDF を回転できる | 壊れた PDF は回転できない（表示はできる） |
| コード | 走査の関数と名前の一覧を保守する必要がある | 1 行の条件 |
| テスト | 今のテストのまま | B 群の 5 テスト（camera、fill_sign、ui）のフィクスチャに xref 表を付ける必要がある（アサーションは変えない） |
| §5 の見逃し | 解消しない | 解消しない |

**推奨**: 一律拒否方式に戻し、条件を「修復や食い違いのあるファイル全部」に広げる。

- 具体的には、`repair_log()` が空でないか `xref_oddities()` が空でなければ、`Indeterminate` にする。古い改訂を開いたものにも同じ条件を当てる。
- §5 の見逃しは、どちらの方式でも残る。そのため、どちらを選んでもこの条件の追加は必要である。
- 回転できる利便性より、「判定の根拠を 1 文で説明できる」ことを優先する。
- 最小の修正案は `rotate_guard.rs` の数行と、上記 5 フィクスチャへの xref 表の追加である。
- 許可方式を残す場合の代わりの案は、次の 3 点:
  - 生の検査を「修復または食い違いがあるときは常に」実行する
  - 拒否する名前をすべて前方一致にする
  - `XRef` も拒否する名前に加える
- 製品コードの修正は、指示どおり行っていない。
