## 3. 確定（commit）と巻き戻しの失敗

監査の結果：確定の記録（`commit_use`）が失敗し、さらに文書からの取り消し（Undo）もできなかった場合、117C ではトースト通知を出すだけだった。名前を付けて保存、印刷、閉じるときの保存の確認から、記録のない押印を含む PDF を出せた。**これが 117D で見つかった安全上の欠陥**。

修正（最小限）：

- エンジンに、文書ごとの保留状態を追加した：`Session::hold_output(id, reason)` と `Document::output_hold()`。一度保留になった文書は、閉じるまで保留のまま。
- 保留中の文書に対しては、次の呼び出しが理由付きの `EditError::Invalid(reason)` を返す：
  - 編集：`apply`
  - 履歴：`undo` / `redo`
  - 保存：`save_bytes`、`save_edited_copy_bytes`、`save_copy_bytes`、`save_full_bytes`
  - 印刷：`print_pdf(_with_pending_text)`
  - 書き出し：`export_data`、`extract`、`split`、`split_by_size`
  - サイズ縮小・最適化：`reduced_bytes`、`optimized_bytes`（`optimize_job`）
  - 注釈の一覧：`summarize_comments`
  - 署名：`sign`、`timestamp_document`、`embed_ltv`
  - 自動保存の `autosave_snapshots` は、保留中の文書を対象にしない。
- 画面側から保留する経路（`hold_seal_doc`）は 3 つ：
  - 確定の記録に失敗し、取り消しにも失敗したとき（`take_back_seal`）
  - 準備後に押印を特定できず、取り消しにも失敗したとき（`finish_seal_prepare`）
  - Undo・Redo・削除の履歴記録に失敗し、文書を元に戻すこともできなかったとき（`revert_seal_step`）
- 理由は「要復旧：…この文書は保存・名前を付けて保存・印刷・書き出し・編集・元に戻す・やり直しができません。保存せずに閉じて、元のファイルを開き直してください。」。通知に加えて、ページの上に閉じられない警告バーとして表示する。

故障ケースごとの結果（すべて自動試験。試験は 13 章）：

| ケース | 結果 |
|---|---|
| 1 準備（prepare）の失敗 | 何も押さない。開いたままの試行も残らない（117C の試験） |
| 2 押印の編集の失敗 | 準備を取り消す（`use_cancelled`）（117C） |
| 3・4 確定の失敗、巻き戻し成功 | 押印を取り除いて取り消しを記録。Redo では戻せない（117C） |
| 5 確定の失敗、巻き戻しも失敗 | **要復旧で保留**。下記の全経路を拒否し、何も書かない（117D の新しい試験） |
| 6 取り消し（`cancel_use`）の失敗 | 押印は取り除き、「未完了の押印準備」として記録が開いたままだと通知する。文書には押印がないので保留しない（新しい試験） |
| 7 結果待ちの間の終了要求 | 拒否して理由を表示する（117C の試験と 7 章の × ボタンの試験） |
| 8 非同期処理の完了直前のタブ切り替え | 準備中なら取り消し（117C）。確定待ちの間なら、押した文書にだけ記録される（新しい試験） |

6 章の区別（承認・準備・作業中の PDF への追加・確定・Undo/Redo・別名保存・印刷）は 117C のとおり。確定の記録から、保存や印刷の成功を推定することはない。保存と印刷の新しい監査記録は追加していない。

## 4. 保存・印刷の拒否

ケース 5 の後、次の経路をすべて試験で確かめた。どれも拒否され、理由が表示された：

- コマンド：`file.save_as`、`print.dialog`、`edit.undo`、`edit.redo`、`edit.text`、`comment.stamp`、`page.rotate`、`page.rotate_ccw`
  - `execute` と `run_command`（メニュー、ショートカット、コマンドパレット、ツールバーは、すべてこの 2 つを通る）
  - `command_enabled` でも無効（灰色）になる
- `file.save` は閲覧専用の方針で、もともと拒否される。
- UI の関数を直接呼んだ場合：`begin_save_copy`、`save_active(As / InPlace)`、`open_print`、`print_now`、`apply_edit`
- エンジンの 12 の呼び出し（3 章の表から抜粋）。自動保存の対象からも外れる。
- 終了：`request_quit` → 保存確認で「保存」→ 理由付きで拒否される。アプリは終了せず、文書は開いたまま、確認がもう一度出る。「保存しない」なら閉じて終了できる。
- 押印の数・使用履歴・フォルダー内のファイルは、どの拒否の後も変わらない。

灰色にするだけでなく、実行経路（エンジン）でも拒否する。リバート確認：

- エンジン側の確認を無効にすると、`apply_edit` が通って試験が失敗した。
- 保留の設定そのものをやめると、「the document is held」で試験が失敗した。

## 5. タイムアウトの原因

`control::transport_tests::an_unauthenticated_connection_is_closed_at_the_deadline`：

- 117C の失敗時の出力は残っていなかった。
- 現状での再現：
  - 単体 50/50 合格（788〜895 ms）
  - `control` モジュールの並列実行 20/20
  - ライブラリ全体の並列実行 3/3
  - 117C と同じ `--test-threads=1` でのライブラリ全体 2/2
  - CPU 負荷を人工的にかけるジョブは、レビューで止められたため実施していない。
- 一時的な診断試験（調べた後に削除）の測定：

| 場面 | 応答が失われた回数 | 応答までの時間 |
|---|---|---|
| 何も送らない接続 | 0/30 | 299〜323 ms |
| 1 バイトずつ送り続ける接続、期限の直後に読む | 1/30 | — |
| 同じ接続、60 ms 遅れて読む | 27 以上/30（出力の表示が途中で切れた） | — |

- 原因：試験の後半は、50 ms ごとに 1 バイトずつ送り続ける。サーバーが期限で接続を閉じた後に次のバイトが届くと、Windows は接続をリセット（RST）し、まだ読んでいなかった理由の行（-32004）を捨てる。そのため、試験側のスレッドが一度に 50 ms 以上止められると、`next_line` が `None` になり「the server says why before closing」で失敗する。CPU 負荷が高いときだけ起きる理由もこれで説明できる。製品の期限（300 ms、受け付け時から数える）自体は常に守られていた。
- 修正（試験の待ち方だけ）：
  - 送信を期限の前（500 ms）に止める。閉じた接続にバイトが届かないので、理由の行は必ず読める。
  - 送信がある場合の期限は 1 s にした。最後のバイトから数える実装なら閉じるのは 1.45 s 以降になり、`< 1.4 s` で区別できる。
  - コードの確認（-32004）、閉じたことの確認、何も送らない場合の確認（300 ms の期限、`>= 250 ms && < 3 s`）は残した。assertion は削除していない。
- リバート確認：サーバーを「読み取りごとに 1 s」の期限（最後のバイトから数える方式）に変えると、「the deadline is absolute: 1.4595024s」で失敗した。
- 修正後：単体 50/50、ライブラリ全体の並列実行 3/3 で合格。
- 別件：修正後のライブラリ全体の並列実行で 1 回だけ、別の試験が 1 件失敗した（計 18 回中 1 回。試験名は記録できていない）。対象の試験はその回も合格していた。原因は**未特定**（15 章）。

## 10. 旧形式の書き戻しの退避

試験コードで旧版の書き込みを模擬した（本物の旧版 SwiftPDF は起動していない）。移行後に旧形式で書かれたファイルは、次の操作のときに、内容をバイト単位でそのまま別名で退避する。退避したことを `legacy_write_set_aside` として記録し、画面で知らせる。退避した内容は取り込まず、旧ファイルの場所には墓石が戻る。117A の検証プログラムでも、別プロセスの旧版による書き込みの検出と退避を確認済み。

1. 実GUIの操作確認（人が行う）。先に `powershell -NoProfile -ExecutionPolicy Bypass -File D:\dev\SwiftPDF-seals-validate\step117d\launch-validation.ps1 -Check` で場所を確認し、`-Check` を外して `fixtures\synthetic-3pages.pdf` を付けて起動する。合成データだけを使い、次を順に確認する：
   - ページ移動とズーム
   - 日本語の表示
   - 一般スタンプと日付スタンプ
   - 理事長印：`fixtures\synthetic-seal.png` を登録し、承認して押印する
   - 回転、Undo/Redo
   - 名前を付けて保存：保存先は `step117d\out` にする。保存した複製を開き直す
   - 印刷プレビュー：表示までにとどめ、実際には印刷しない
   - 登録中や押印直後に × ボタンを押す
   - 2 つ目の起動（`--new-window`）で、同じフォルダーから登録・削除する
2. 名前を付けて保存は Windows 標準のファイル選択画面を使う。この画面は「最近使ったフォルダー」を Windows がレジストリに記録する。アプリの外の OS の動作だが、これも避けたい場合は、名前を付けて保存の確認を省いてよいか判断してほしい。
3. 48 MiB 以上で記録 1 回に最大 10 秒かかることを、v1.0.0 で許容するかどうか。

## 15. 残るリスク

- 実GUIの操作確認は未完了（6 章）。
- 要復旧にする経路のうち、試験で直接再現したのは `take_back_seal` の経路だけ。`finish_seal_prepare` と `revert_seal_step` の経路は同じ関数を呼ぶことをコードで確認したが、故障を起こす試験はない。
- `take_back_seal` は、取り消す前に「Undo の先頭が "Add stamp" であり、その押印がまだ文書にある」ことだけを確かめる。もし別の一般スタンプが先頭にあれば、そちらを取り消してしまう。確定を待つ間はすべての編集を拒否するので、利用者の操作では起こらない。仮に起きても、押印が残るため要復旧で保留になり、外には出ない（試験の作成中に、ゲートを迂回したときだけ観測した）。
- 名前を付けて保存の画面に答えた後の書き込み（`write_save_copy`）でも保留を確認するが、ファイル選択画面を伴うため試験はない。エンジン側の拒否が最後の防御になる。
- 結合（Combine）は、開いている文書のバイト列を UI が直接読む。閲覧専用モードでは結合のコマンド自体を拒否するので、そこから出ることはないが、エンジン側の保留の対象ではない。
- 5 章の、別の試験の 1/18 の失敗は原因が未特定。
- 大きなストア（11 章）の遅さによる Busy。

- データの安全性（記録のない押印が外へ出ないこと、履歴が失われないこと、移行の安全性）は、自動試験とリバート確認で条件を満たした。
