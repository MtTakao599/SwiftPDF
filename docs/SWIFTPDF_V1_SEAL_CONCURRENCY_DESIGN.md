## 3. `seals.bin` の保存形式

- 先頭は `SWSEAL1\n`（8 バイト）。続きは DPAPI の暗号文である。
- 平文は JSON の `FileBody { seals: [StoredSeal], history: [StoredEvent] }`。
  - `StoredSeal`: `name`、`file`、`width`、`height`、`data`（PNG の base64）、`scale`（v0.6 で追加）、`effects`（v0.7 で追加）
  - `StoredEvent`: `at`（UTC の文字列。秒単位）、`file`、`page`、`seal`、`event`、`processed`、`angle_deg`、`fade`、`seed`、`image_sha256`、`rotation_mode`
  - 追加された欄はすべて `#[serde(default)]`。未知の欄は無視する（`deny_unknown_fields` は無い）。
- スキーマ版: 欄としては無い。先頭の `SWSEAL1` が実質的な版になる。
- レコード ID: 無い。
  - 印影は `name` で一意（登録時に重複を拒否する）。ただし UI は添字で扱う。
  - 履歴の行には ID が無い。時刻は秒単位なので、同じ秒の同じ操作は区別できない。
- 読み込み時の検査（`decode_file`）:
  - 印影が 8 件を超えるか、**履歴が 400 行を超える**と、ファイル全体を「復号できない」扱いにする。
  - 印影の検証（`validate_seal`）に失敗した場合と、`event` が 5 種類以外の場合も同じ。
- 上限:
  - 平文は 16 MiB（`MAX_PLAINTEXT`）。
  - PNG は 1 件 2 MiB。2 MiB の印影 8 件は base64 で約 22 MiB になり、16 MiB を超える。この場合は、7 件目あたりで登録が「印影を保存できませんでした」で失敗する。データは失われない（計算上の観察。未試験）。

## 4. DPAPI の利用方法

- `windows_dpapi::encrypt_data(data, Scope::User, None)`。追加エントロピーは無い。
- 同じ Windows ユーザーなら、同じ PC で、パスワードを変えた後も復号できる。別ユーザーと別 PC は復号できない。
- 暗号文を改ざんすると、DPAPI の整合性検査で復号に失敗し、ロック状態になる。ただし、このユーザーとして動くプログラムは、復号して書き換え、暗号化し直せる。DPAPI は、同じユーザーによる改ざんの証拠にはならない。
- エラー文は固定の文言で、データを含まない。`seal_store.rs` と `stamps_ui.rs` の印影の経路に、ログ出力は無い。

## 5. 複数起動時の競合原因

1. 各プロセスは、起動時に読んだ内容をメモリに持ち続ける。
2. 変更のたびに、そのメモリ全体を書く。他プロセスの変更を読み直さない。
3. 排他制御が無い。

このため、プロセス A が起動したあとに、別のプロセスが何かを書くと、**A が次に何かを書いた時点で、その変更はすべて消える**。履歴 1 行の追加でも消える。ファイルは原子的に置き換えるので、壊れはしない。最後に書いたプロセスのメモリが、そのままファイルになる。

複数プロセスになる経路:
- 単一インスタンスの引き渡しは、ファイルだけを指定した起動に限られる（`main.rs` 217 行）。
- スタートメニューの 2 回起動、ファイル無しの起動、オプション付きの起動、`--new-window` は、別プロセスになる。
- 引き渡しに数秒で失敗した場合も、別プロセスになる。
- 同じユーザーの別セッション（リモートデスクトップとコンソールなど）は、ソケットがセッションごとなので別プロセスになり、同じ `%LOCALAPPDATA%\SwiftPDF\seals.bin` を書く。
- 同じポータブルフォルダから起動した 2 つのプロセスは、同じ `Data\seals.bin` を書く（ソケットの扱いは未確認）。

## 7. 登録、使用、承認、削除の競合

| 競合 | 影響 |
|---|---|
| 登録と登録 | 先に書いた方の登録が消える（A） |
| 登録と使用 | 使用を書いた側が古い一覧を持っていれば、相手の登録が消える（A の後半） |
| 使用と使用 | 先に書いた方の履歴が消える（B、D） |
| 削除と、倍率・加工・使用 | 削除した印影が復活する（C1、C2）。削除した側の画面には無いが、ファイルには戻る |
| 押印失敗の取り消し | `pop_event` が他プロセスの行を巻き添えにする（C3）。現行でも、メモリ全体の書き戻しで起きる。読み直して最後の行を消す方式に変えると、**他プロセスの行そのものを消す**危険がある |
| 承認 | 承認（`SealApproval`）はメモリにだけあり、ファイルには入らない。そのため、承認状態がファイルで巻き戻ることは無い。ただし、他プロセスで削除された印影を、こちらのプロセスでは承認して押せる（C2） |

認証の迂回と権限昇格:
- 理事長印には、パスワードや PIN による認証が**もともと無い**。承認は、同じ利用者がダイアログでチェックを入れる確認である。
- 競合で、承認のチェックを飛ばして押印する経路は見つからなかった。承認の照合（`approval_matches` と画像の SHA-256）は、プロセスの中で完結している。
- 権限昇格も無い。別の Windows ユーザーはファイルを復号できない。
- 問題は「削除・変更の取り消しが、他プロセスによって無効になる」ことと、「監査記録が黙って消える」ことである。重大な認証迂回ではないと判断し、停止条件には当たらないとした。

## 8. 400 件上限の正確な仕様

- 実装: `append_event`（`seal_store.rs` 312〜330）。`MAX_HISTORY = 400`。
- 対象: **ファイル全体**の履歴。印影ごとではない。`confirmed`、`undone`、`redone`、`removed`、`removal-undone` がすべて同じ 1 本の履歴で、承認の記録と使用の記録は分かれていない。`confirmed` が承認済みの押印の記録を兼ねる。
- タイミング: 401 行目を追加したとき、メモリ上で最も古い行を消してから書く。
- 実測:
  - 400 行目は追加でき、400 行すべてが残った（`h-000`〜`h-399`）。
  - 401 行目の追加は `Ok` を返した。結果は 400 行で、`h-000` が消え、`h-001`〜`h-400` が残った。
- 通知: 無い。成功として扱う。
- 外部への出力: 履歴の書き出し、表示、バックアップの機能は無い。履歴を画面で見る手段も無い。
- 読み込み側: 401 行以上あるファイルは「復号できない」扱いになり、ロックされる。実測では、ファイルを変えず（バイト一致）、印影の登録も拒否した。
  - 上限を上げた新版が書いたファイルを旧版で開くと、旧版は理事長印を使えなくなる。ただし上書きもしない。
- 押印の失敗による `pop_event` は、最後の行を物理的に消す。監査の観点では、「取り消した」という行を残す方が望ましい（16 節）。

### 上限の 3 案

計測条件: 256×256 のノイズ PNG（138,692 バイト）を 8 件、履歴の 1 行は約 265 バイト。

| 履歴 | 平文 | 暗号化して書く | 読んで復号 | 現行ビルドで開けるか |
|---|---|---|---|---|
| 400 | 1.60 MB | 181 ms | 132 ms | 開ける |
| 4,000 | 2.66 MB | 248 ms | 195 ms | 開けない（上限） |
| 40,000 | 13.2 MB | 1,134 ms | 771 ms | 開けない（上限） |

400 行は現行の書き込み経路で計測した。4,000 行と 40,000 行は、同じ処理を検証プログラムで再現して計測した。

| 案 | 評価 |
|---|---|
| A 無制限保持 | 押印のたびにファイル全体を暗号化して書くので、時間は行数に比例する。4 万行で約 1 秒になる。平文の上限 16 MiB があるので、実際には無制限にならない（約 5 万行と印影で到達する）。旧版はロックする。一度壊れると全履歴を失う（単一ファイル）。単独の案としては推奨しない |
| B 上限で追加を拒否 | 押印は「履歴を書けなければ押さない」設計なので、上限に達した時点で理事長印が使えなくなり、業務が止まる。回復には、履歴の書き出しや退避の手段が別に必要。警告（例: 380 行で予告）と組み合わせても、単独では不十分 |
| C 別ファイルへ退避 | 利用中の `seals.bin` は小さく保ち、古い履歴を追記専用の監査ログへ移す。監査ログも DPAPI で暗号化する（1 行ずつ、または一定行数のまとまりごと）。前の行のハッシュをつないで、削除や並べ替えを検出できるようにする。ファイル間の整合は、同じロックの中で「退避を書いてから `seals.bin` を縮める」順序で取る。失敗しても、二重に残るだけで、消えない。バックアップは 2 ファイルが対象になる。同じユーザーによる改ざんは、防げない（4 節） |

推奨: **C**（v1.0.0 での最小形は「400 行を超えた分を、消さずに退避ファイルへ移す」）。加えて、上限が近いことと退避先を知らせる。B は C の退避に失敗したときの最後の手段として残す（押印を止め、理由を示す）。

## 9. 単一起動案（方式 1）の評価

- 実装: `single_instance::claim` の引き渡しを、ファイル無しの起動にも広げる（既存ウィンドウを前に出す）。規模は小〜中。
- 起動時の UX: 2 回目の起動は既存ウィンドウに切り替わる。Office と同じで、分かりやすい。
- 防げない経路:
  - `--new-window` とオプション付きの起動
  - 引き渡しの失敗時の自前ウィンドウ（設計上のフォールバック）
  - 同じユーザーの別セッション（ソケットがセッションごと）
  - 同じ `Data` を指す複数のポータブル起動
  - 旧版との同時起動
- クラッシュ後: ソケットが残っても、接続できなければ新しい主プロセスになる（既存設計）。
- 評価: **共有データの更新競合を防ぐ手段としては不十分**。体験の補助としてだけ使う。

## 10. 排他制御と再読込（方式 2）の評価

### ロックの手段

| 候補 | 評価 |
|---|---|
| `std::fs::File::lock` / `try_lock`（Rust 1.89 から安定。Windows では `LockFileEx`） | **第一候補**。依存の追加も `unsafe` も要らない。プロセスの終了やクラッシュで、OS がハンドルを閉じてロックを解放する。待ち時間の上限は `try_lock` と短い待機の繰り返しで作る |
| 名前付きミューテックス（Win32） | `unsafe` か新しい依存が要る。ポータブルの保存先ごとに名前を作る必要がある。採らない |
| `create_new` で作るロックファイル | クラッシュするとロックが残る。採らない |

### ロック対象

`seals.bin` は rename で置き換わるので、ファイル自体はロックできない（置き換わると別のファイルになる）。そこで、同じフォルダの固定名 **`seals.bin.lock`** を、開いたままロックする。

- 保存先が `seals.bin` の場所から決まるので、通常版とポータブル版で自然に一致する。
- 同じ `Data` を使うプロセスは、同じロックを使う。
- ロックファイルの中身は空で、データは入れない。

### 手順（読み込みと書き込みを 1 回のロックで包む）

1. `seals.bin.lock` を開き、待ち時間の上限（例: 3 秒）付きでロックを取る。取れなければ、変更を適用せずに「ほかの SwiftPDF が印影ファイルを使用中です。もう一度お試しください。」を返す。登録の下書きや仮置き、承認は保持する。
2. `seals.bin` を読み直して復号する。ロック状態（復号できない）なら書かない（現行と同じ）。
3. 依頼された**1 つの操作**を、読み直した最新の内容に適用する。スナップショット同士の自動マージはしない。

   | 操作 | 適用の規則 |
   |---|---|
   | 履歴の追加 | 末尾に追加するだけ。追加専用なので、安全なことを示せる |
   | 登録 | 同名がもうあれば拒否。8 件を超えるなら拒否 |
   | 削除 | 名前と画像の SHA-256 が、このプロセスが見ていたものと一致すれば削除。無ければ「既に削除されています」。違えば拒否（方式 3） |
   | 倍率・加工 | 名前と画像が一致する場合だけ変更する。添字は使わない |
   | 押印失敗の取り消し | 最後の行ではなく、自分が書いた行だけを、内容の一致で取り除く（行の ID を入れるなら ID で）。または取り消しの行を追記する（16 節） |

4. JSON にし、DPAPI で暗号化する。
5. 一時ファイルに書き、`sync_all` で flush する（既存の `write_atomically`）。
6. rename で置き換える。
7. メモリ上の `library` を、書いた内容にする。他プロセスの変更が、ここで画面に入る。
8. ロックを解放する（ハンドルを閉じる）。

### 読み取りだけの更新

- 印影一覧を開くとき、押印を確定する前、削除の前に、ロックを取って（または短く）読み直し、画面の一覧を最新にする。
- 押印の確定では、ロックの中で「名前の印影が存在し、承認した画像の元になった PNG と一致する」ことを確かめる。消えていれば押印しない。これで C2 を防ぐ。
- `QuickTool::ChairmanSeal(index)` の添字は、読み直しでずれる。選択は名前で持ち直す。

### そのほかの論点

| 論点 | 評価 |
|---|---|
| ロックと保存先の一致 | 同じフォルダの固定名なので一致する。ネットワークドライブの SMB でもバイト範囲ロックは効くと考えられる（実機は要確認）。OneDrive などの同期フォルダは対象外（16 節） |
| 異常終了 | ハンドルの解放で OS がロックを外す。一時ファイルが残ることはある（`.seals.bin.pdfcraft-*.tmp`）。ロックの中で、古いものを片付けてよい |
| 待ち時間の上限 | 3 秒程度。UI スレッドで待つので、長くしない。待つ処理はディスクの読み書きと暗号化だけで、数百ミリ秒（8 節の計測） |
| 全プロセスが同じ規則に従うか | 新版どうしは従う。**旧版はロックを知らない**（13 節） |
| ロック失敗時 | 変更を捨てない。操作を拒否し、入力を保持する |
| 保存失敗時 | 既存ファイルはそのまま（rename の前に失敗する）。メモリは、読み直した最新の内容に戻す |

## 11. 楽観的競合検出（方式 3）の評価

- 読み込み時に、ファイルの SHA-256（または、平文に入れる世代番号）を覚えておく。書く前に、ロックの中で比べる。
- 単独では、比較と書き込みの間に競合が起きる。ロックと組み合わせれば、その窓は無くなる。
- 役割:
  - 「最後に読んだあと、ほかのプロセスが変えた」ことを知って、画面を最新にし、利用者に知らせる。
  - 印影の削除と変更で、「見ていたものと違う」ときに拒否する。
- 世代番号を平文に入れるかは、形式の変更に当たるので判断事項（13 節）。ファイルのハッシュでよければ、形式は変わらない。
- 履歴の追加には、拒否は要らない（追加専用）。

## 12. 推奨設計

1. **方式 2（`seals.bin.lock` によるプロセス間排他）と、ロック内での読み直し**を必須にする。
2. 変更は「最新の内容に、依頼された 1 つの操作を規則どおりに適用する」ものに限る。スナップショットの自動マージはしない。
3. 印影の削除と変更には**方式 3**の一致確認を入れ、違えば拒否する。
4. 押印の確定は、ロックの中で印影の存在と画像の一致を確かめ、履歴を書いてから行う。履歴を書けなければ押さない（現行の原則を維持）。
5. `pop_event` の「最後の行を消す」をやめる。自分の行だけを取り除くか、取り消しの行を追記する（16 節）。
6. 履歴は消さない。上限を超えた分は退避ファイルへ移す（8 節の C）。
7. 単一起動の拡張（方式 1）は、体験の補助として任意で行う。
8. 旧版の書き込みを締め出すかは 13 節で判断する。

## 13. 既存データ形式との互換性

- 現行の `SWSEAL1` と JSON は、そのまま読める設計にする。ロックファイルは別ファイルなので、形式は変わらない。
- 行の ID などの欄を追加しても、旧版は未知の欄を無視して読める。ただし、**旧版が書き戻すと、その欄は消える**。
- 欄を足しても、スキーマ版の欄が無いので、旧版の書き込みを検出できない。

### 旧版との同時起動（新しいロックだけでは安全にならない）

- v0.6〜v0.9 の SwiftPDF は、ロックを取らず、読み直しもしない。新版がロックしていても、旧版は起動時の内容で上書きできる。
- **新版のロックだけでは、旧版との共存を安全にできない。**
- 検出の方法:
  - 世代番号かハッシュで、外部での置き換えを検出する。ただし、消失を防ぐことはできず、事後に知るだけである。
- 締め出す方法（案）:
  - 新版が書くファイルの先頭を `SWSEAL2\n` にする。
  - 旧版の `decode_file` は、先頭が `SWSEAL1\n` でなければ「復号できない」としてロックし、**ファイルを書かない**。これは実測した 401 行のファイルと同じ挙動である。
  - こうすると、旧版は理事長印を使えなくなる代わりに、新しいデータを上書きできない。
  - 新版は `SWSEAL1` も `SWSEAL2` も読む。最初に書くときに `SWSEAL2` へ移行する。
  - 移行の直前に、同じフォルダへ `seals.bin.v1-backup`（暗号文の写し）を作る。復元は、同じユーザーと同じ PC に限る。
  - 一方向の移行なので、旧版へ戻すと理事長印が使えない。リリースノートへの記載が必要。
- MSI の更新インストール: 旧版を動かしたまま更新した場合、旧版がメモリ上の古い内容で書き戻す可能性がある。インストーラーで旧版の終了を求めることを、要確認として残す。

## 14. 保存失敗時の復旧

| 失敗 | 現行 | 推奨 |
|---|---|---|
| ロックが取れない | （ロックが無い） | 操作を拒否し、入力（下書き、仮置き、承認）を保持して、再試行できるようにする |
| 暗号化の失敗 | 拒否し、メモリを戻す | 同じ |
| 書き込みや flush、rename の失敗 | 拒否し、メモリを戻す。既存ファイルはそのまま | 同じ。メモリは読み直した最新の内容に |
| 復号の失敗 | ロックし、ファイルはそのまま | 同じ。加えて、保存場所と、Windows ユーザーや PC の違いを説明する |
| 登録の失敗 | 下書きは消える | 下書きを残す（ダイアログを閉じない） |
| 押印後に文書への適用が失敗 | `pop_event`（最後の行） | 自分の行を特定して取り除くか、取り消しの行を追記する |
| Undo / Redo で履歴を書けない | 文書の変更を戻す（既存） | 同じ。ロックで待たされた場合も、同じ扱い |

## 15. ロックと書き込みの安全性

- ロックは `seals.bin.lock` だけに掛け、データの置き換えは既存の原子的書き込みで行う。
- ロックの中でしか `seals.bin` を書かない。読み取りだけの更新も、ロックの中で読むと、置き換えの途中に当たらない（rename は原子的なので、ロック無しでも途中状態は読まない。実測でも破損は 0 件）。
- ロックの保持は、1 回の読み込み、適用、暗号化、書き込みの間だけにする。UI の操作をまたいで保持しない。
- 待ち時間の上限で、UI が固まらないようにする。
- `sync_all` の後に rename する（既存）。親フォルダの永続化は約束しない（既存のコメントどおり）。
- ロックファイルの作成に失敗した場合（読み取り専用のフォルダなど）は、書き込みを拒否する。黙ってロック無しで書かない。

## 16. 監査履歴の保全方針

- **監査記録を永続化できない状態では、理事長印の重要な操作（押印、削除の記録、Undo / Redo）を成功扱いにしない。** 現行の「履歴を書けなければ押さない」「文書を戻す」を維持し、ロックの失敗も同じ扱いにする。
- 履歴を黙って消さない。
  - 上限で消す処理をやめ、退避に変える。
  - `pop_event` による物理削除は、取り消しの行の追記に変えることを推奨する。新しい種類の行は旧版が読めずロックするので、13 節の `SWSEAL2` と一緒に扱う。
- 現行 UI との整合:
  - 承認はプロセス内の確認のまま。ロックの中での照合を加えるだけで、操作手順は変わらない。
  - 履歴を見る画面と、書き出しは無い。退避ファイルの存在を利用者に知らせる場所を、新しく決める必要がある（判断事項）。
- 改ざんと競合の区別:
  - ロックの下では、競合は起きない。ハッシュや世代番号の不一致は「この SwiftPDF の外で変更された」（旧版、手作業の復元、改ざん）として扱う。
  - それ以上の区別はできない。同じユーザーによる改ざんは、DPAPI では防げない（4 節）。退避ログのハッシュの連鎖で、削除や並べ替えを検出できるだけである。
- ログ漏えい: 現状、印影、鍵、平文はログに出ない。新しいコードでもログに出さない（エラー文は固定）。

## 17. 推奨する実装範囲

### STEP 117 案（v1.0.0 必須）

- `seal_store.rs`:
  - `seals.bin.lock` による排他と、ロック内での読み直し。
  - 操作ごとの適用規則（名前と画像の一致、追加専用の履歴、自分の行の取り消し）。
  - 書いた後にメモリを最新にする。
- `stamps_ui.rs`、`editing.rs`、`dialogs.rs`:

  - ロック失敗時の通知と入力の保持。
  - 登録の失敗時に下書きを残す。

  - 単一起動の拡張（任意）
